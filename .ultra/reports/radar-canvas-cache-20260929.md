# 雷达画布开销定向优化

- 基线：`46e78ef`。GLM-5.3 旗舰在独立只读上下文核查近期代码与历史验收，未找到高置信度的对局逐帧回归；大厅按需加载改动未增加对局每帧成本。历史低帧率采样分别受低电量模式或主机竞争影响，不能据此认定代码回退。
- 确定的既有开销：`HUD.drawRadar()` 原先每帧赋值 `canvas.width` 和 `canvas.height`，即使值未变也会重置画布；每帧还重建同尺寸径向渐变。
- GLM-5.3-Flash 按测试先行修复：仅在对应尺寸变化时赋值画布宽或高；渐变按实际后备尺寸缓存，尺寸变化时重建。独立检查指出初稿在单轴变化时多重设另一轴，已交回 Flash 修正。
- 验证：`node --test tests/unit/hud-radar.test.mjs` **4/4**；`npm run build` 离线、Y8、GameMonetize 三目标成功；`git diff --check` 通过。测试覆盖首帧、尺寸不变、仅宽变化、仅高变化，并记录画布重设与渐变创建次数。
- 性能界限：这是逻辑操作次数的确定性减少，尚无可比较的 FPS 增益数字。2026-09-29 交流供电且 `lowpowermode=0`；00:24 VMware 约 102% CPU、主机 load 约 10，00:41 VMware 仍约 50%、另一个工程的 Python 任务约 67%、主机 load 升至约 16。待竞争负载暂停后只跑一次双地图 1080p 中画质串行复测。
